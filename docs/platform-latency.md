# 통합 관리 플랫폼 응답 지연 측정

사용자가 제공한 사업계획서 설명의 **페이지/기능 호출부터 콘텐츠 표시 완료까지의 평균 응답 지연**을 현재 플랫폼에서 반복 측정하는 자체 측정 도구입니다. 2026년 목표값은 사용자 제공값인 **2.5초**로 설정했습니다. 계획서 원문 전체나 공인 시험 절차를 검증한 결과는 아닙니다.

## 실행

```sh
npm ci
npx playwright install chromium
npm run test:platform-metrics
npm run measure:platform                         # 기본: 사용자 1명, 각 항목 5회
npm run measure:platform -- --repeats 3           # 각 항목 3회
npm run measure:platform -- --vus 1,5 --repeats 10 # 별도 동시 부하 비교
npm run measure:platform -- --help
```

- 기본 실행은 사용자 1명 × 13개 항목 × 5회 = **65회**입니다. 각 항목을 연속 5회 측정한 뒤 항목 평균을 출력하고 다음 항목으로 이동합니다. 워밍업 13회는 별도로 표시하고 평균에서 제외합니다.
- 콘솔과 HTML, `trials.csv`는 **항목 / 1회 / 2회 / 3회 / 4회 / 5회 / 항목 평균** 표와 마지막의 화면·기능·전체 항목 평균을 제공합니다. `--repeats 3`이면 3개 회차 열로 바뀝니다. 동시 사용자 수를 늘리면 `1회/사용자1`처럼 구분해 개별 시간을 남깁니다.
- `--vus 1,5`: 동시 사용자 1명, 5명 프로필을 차례로 실행합니다. 시나리오마다 해당 수의 독립 브라우저 컨텍스트를 병렬로 실행하고 모두 끝나면 다음 시나리오를 시작하는 닫힌 부하 모델입니다. 일정한 초당 요청률은 아닙니다.
- `--repeats 10`: 기본 5회 대신 10회로 지정하는 예입니다. 프로필별 각 사용자·시나리오당 10회. 총 본 측정은 `(1+5) × 13 × 10 = 780회`입니다. 프로필별 각 시나리오 1회 워밍업은 별도 저장하고 통계에서 제외합니다. 1명 프로필의 시나리오별 표본은 10개, 5명은 50개입니다.
- `--target-ms 2500`, `--timeout-ms 30000`: 평균 목표와 준비 조건 대기 제한. 실패한 표본을 임의의 타임아웃 값으로 평균에 넣지 않으며, 실패 수를 공개하고 실패가 있으면 충족 판정을 하지 않습니다.
- `--output PATH`: 기본값은 `.runtime/platform-latency/<UTC timestamp>`. 기존 `samples.jsonl`이 있는 경로는 덮어쓰지 않고 종료합니다.
- 브라우저는 매회 새 컨텍스트를 사용하므로 페이지별 HTTP 브라우저 캐시·세션은 새 상태입니다. 브라우저 프로세스 시작 시간은 제외하고 서버/OS 캐시는 비우지 않습니다. 기능 측정은 준비 화면 로딩을 제외한 클릭 이후이며 준비 화면에서 이미 받은 리소스는 재사용합니다.
- API/웹의 기능을 변경하거나 저장·삭제·학습/추론 작업을 제출하지 않습니다. `POST /api/reconstructions/preview`는 저장 없는 미리보기만 계산합니다.

프로그램 종료 코드는 성공 및 목표 충족 `0`, 측정 구성·준비 오류 `1`, 본 측정 실패 또는 전체 항목 평균 목표 미충족 `2`입니다. 개별 화면의 충족 여부는 요약에 별도로 기록됩니다. 특정 화면의 평균이 초과하더라도 전체 평균과는 구분합니다.

## 무엇을 재는가

HTTP 타이밍만으로는 React 화면의 데이터 바인딩·이미지 디코딩·결과 표 표시를 확인할 수 없어 Playwright의 실제 Chromium을 사용합니다. [JMeter 공식 설명](https://jmeter.apache.org/#)에서도 JMeter 자체는 JavaScript를 실행하거나 브라우저처럼 HTML을 렌더링하지 않는다고 구분합니다. JMeter를 활용한 정식 부하 시험이 필요하면 별도 부하 발생과 이 브라우저 완료 측정을 함께 운영할 수 있습니다.

페이지 측정 시작점은 Navigation Timing의 시간 원점입니다. 기능 측정 시작점은 실제 클릭 이벤트를 capture한 `performance.now()`입니다. 완료는 다음 조건을 만족한 상태에서 연속 두 번의 추가 `requestAnimationFrame` 기회를 지난 시점입니다.

1. 문서 load가 완료되고 현재 화면의 로딩 표시가 사라졌습니다.
2. 화면별 사전 조회한 행 수·작업 ID·결과 필드 수·학습 손실 점 수가 DOM과 일치하고 필요한 API의 응답 본문 전송이 끝났습니다.
3. 현재 페이지의 **모든 이미지**가 성공적으로 디코딩됐고 폰트 로딩이 끝났습니다. 첫 화면 아래 이미지까지 포함하도록 현재 페이지의 `loading=lazy`를 `eager`로 전환합니다. 이는 보수적인 측정용 조작이며 다른 페이지의 데이터까지 가져오지는 않습니다.
4. 학습 모니터는 해당 작업 로그 API와 실제 로그 길이까지 확인합니다. 드리프트 화면은 별도의 AI 재레이블링 비교 보고서 API도 포함합니다.

이는 DOM·리소스 및 렌더 프레임으로 정의한 **화면 표시 완료의 대리 지표**입니다. 실제 모니터의 스캔아웃까지 재는 광학 측정은 아닙니다. 모든 접힌 상세를 사용자가 펼치거나 전체 데이터셋을 내려받는 시간도 아닙니다. `networkidle`에 고정된 정숙 시간을 추가하지 않으며, 주기적 상태 조회가 끝나지 않는다는 이유로 측정을 무한 대기하지 않습니다. [Playwright 공식 문서](https://playwright.dev/docs/api/class-page#page-wait-for-load-state)에서도 준비 상태 확인에 `networkidle` 사용을 권장하지 않습니다.

## 시나리오와 완료 조건

| 구분 | 시나리오 | 주요 완료 조건 |
| --- | --- | --- |
| 화면 | 워크스페이스 목록 | 전체 워크스페이스 카드·메타데이터 |
| 화면 | 무신사 데이터 | 현재 버전 첫 페이지 최대 24개 샘플과 이미지 전체 |
| 화면 | GS SHOP 데이터 | 현재 버전 첫 페이지 최대 24개 샘플과 이미지 전체 |
| 화면 | 데이터 재구성 설정 | 데이터셋 선택 목록·초기 선택값 |
| 화면 | 모델 목록 | 전체 모델 행 |
| 화면 | 학습된 모델 상세 | 실제 LoRA 모델명·학습 연결 링크·모델 메타데이터 |
| 화면 | 모델 학습 설정 | 데이터/모델 선택 옵션과 활성화된 요청 버튼 |
| 화면 | 모델 평가 결과 | 선택 작업 ID, 전체 속성 점수 행, 샘플별 결과 DOM |
| 화면 | 학습 모니터링 | 선택 작업 ID, 전체 손실 곡선 점, 실행 로그 |
| 화면 | 드리프트 결과 | 선택 작업 ID, 전체 속성 분포, 재레이블링 비교 보고서 |
| 기능 | 레이블 상세 열기 | 대화상자·속성 사전·편집 필드·확대 이미지 |
| 기능 | 재구성 미리보기 | 계산 API·미리보기 fingerprint·완료 메시지 |
| 기능 | 과거 드리프트 선택 | 새로 선택한 작업의 ID·상세 API·전체 결과 필드 |

실제 데이터가 있는 환경을 대상으로 합니다. 무신사/GS SHOP, 사용 가능한 학습 모델, 가장 최근의 완료된 학습·평가·드리프트 및 과거 드리프트 결과가 필요합니다. 준비 데이터가 부족하면 시나리오를 빼고 좋은 평균을 만드는 대신 준비 오류로 중단합니다. 실행 중 데이터/선택 작업이 바뀌면 조건 불일치 실패가 날 수 있습니다.

## 결과와 판정

- `report.html`: 열어서 확인할 수 있는 독립 HTML 보고서.
- `report.json`: 환경·서비스 상태·작업 큐·데이터 버전·완료 조건·그룹 통계·호스트 모니터링. 코드 SHA256과 Git 상태도 기록합니다.
- `trials.csv`: Excel에서 읽을 수 있는 UTF-8 BOM CSV. 회차별 초 단위 시간·항목 평균·전체 평균. 복수 사용자 프로필은 표를 구분해 저장합니다.
- `summary.csv`: 시나리오별 평균, p50, p95, 최댓값, 초과 수, 실패 수.
- `samples.jsonl`: 워밍업과 본 측정의 개별 원시 표본. 페이지는 Navigation Timing, API는 Resource Timing을 보조값으로 보관합니다. **API 평균을 화면 응답 평균으로 대체하지 않습니다.**
- `monitor.json`: 1초 간격 부하 생성기 호스트 CPU 사용률·load average·가용 메모리·드라이버 RSS. 동일 호스트에서는 서버와 브라우저의 합산 부하입니다. 원격 대상이면 서버 측 모니터링은 별도로 수집해야 합니다.
- `before.json`: 준비 상태의 증거. 준비 검사가 중단돼도 보관합니다.

항목 평균은 해당 항목의 성공한 표본 합 ÷ 성공 횟수입니다. **전체 항목 평균 = 항목별 평균의 합 ÷ 항목 수**로 각 항목의 가중치를 동일하게 적용합니다. 화면 10개와 기능 3개도 각각 항목 평균을 내어 별도로 표시합니다. 모든 항목을 같은 횟수 측정하고 실패가 없으면 전체 개별 측정값의 산술평균과 같습니다. p50/p95는 nearest rank이며 보조 통계로 유지합니다. 표시만 소수 셋째 자리로 반올림하고 계산은 원시 정밀도를 사용합니다. 실패는 회차 칸에 `실패`로 표시하고 0초로 바꾸지 않습니다. 실패한 항목의 평균은 `성공분 평균`, 전체 판정은 `불완전 · 판정 불가`로 표시합니다. 유효 표본이 전혀 없는 항목이 있으면 그 항목을 빼고 전체 평균을 만들지 않고 `계산 불가`로 표시합니다. 2.5초는 평균 목표이며 개별 표본의 초과율이나 p95와 동일한 기준이 아닙니다.

HTTP 오류·JavaScript 예외·실패한 이미지·준비 시간 초과는 실패로 보관합니다. Next.js가 취소한 **명시적인 prefetch 헤더가 있는 `ERR_ABORTED` 요청만** 탐색 준비 요청으로 분리 기록하며, 실제 데이터/이미지 요청 실패를 무시하지 않습니다.

## 평가 범위

이번 사용자의 선택은 **현재 18091 통합 플랫폼만**입니다. 웹/API/워커와 저장된 실제 학습·평가·드리프트 결과의 연결을 확인하지만, 과제 내 다른 독립 플랫폼·메타데이터 도구 전체를 활성화하고 연계했다는 증거는 아닙니다. 서비스가 활성화된 것과 모든 GPU 작업이 부하를 발생시키는 것은 구분합니다. 실행 전후 작업 큐·GPU 사용률과 로컬 서비스 상태를 보고서에 남깁니다.

동일 서버에서 브라우저를 실행하면 자원 경쟁으로 느려지는 효과와 짧은 네트워크 경로로 빨라지는 효과가 공존합니다. 평가용 수치를 확정하려면 독립 부하 생성기, 합의된 동시 사용자 수·네트워크·데이터 크기·기능 가중치·도구 연계 범위를 고정해 재측정해야 합니다. 이 스크립트의 결과는 현재 구성의 자체 측정이며 공인시험 또는 사업계획서 전체 요건 충족 판정을 대신하지 않습니다.
